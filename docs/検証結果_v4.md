# cas_auto_report 検証結果 v4（操作後の待ち：wait_after）

実施日: 2026-08-28 ／ 実施者: ワーカー（実装・検証担当）
対象: 設計書「v3 追記（2026-08-28）：操作後の待ち（wait_after）」の実装と実測

本物の業務システムで起きた「帳票画面に着くと自動で印刷プレビューが始まり、その作成中（くるくるが出ている間）に
プレビューボタンを押すと押下が無効になる」症状への対策。**待つ場所を記録時に人が指名し、決めた秒数だけ待つ**方式を実装した。

**練習ページに「押した後しばらく反応しない画面」を足し、印を付けない再生で症状を再現させ、印を付けた再生で通ることを実機Edgeで確かめた。**
併せて既存の G2・G6・G9・G7 を再実測した。

## 2. 実装したもの（設計書v3追記のとおり）

### 2.1 記録時（`-Record`）

出力実行ボタンの選択の**直後に**、続けて次を聞くようにした。

```

```

- 全手順が対象（click に限らず goto / fill / setcheck / expect_url も選べる）
- 複数可（カンマ区切り。空白が混じってもよい）／Enterのみなら設定しない

一覧の書式は、記録中に出している手順一覧と**同じ番号・同じ書式**。
そのために説明行を作る処理を `Get-ActionDesc` に1本化し、記録中の表示と待ちの指名の表示で共有した。

### 2.2 再生時

`wait_after: true` の手順は、**その手順を実行した後に `wait_after_ms` だけ待つ**（`Start-Sleep`。画面の状態は見ない）。
待っている間は `  (操作後の待ち: 5000 ms)` と画面に出る。
`-DryRun` でも同じように待つ（実測は §6）。

## 3. 練習ページに足したもの（`test/mock/slow.html`）

**既存の `app.html` / `spa.html` は作りを変えていない**（G2・G6・G9 が今回の追加に影響されないようにするため）。
新しい画面は別ページとして足し、メニュー（`index.html`）に入口を1行だけ追加した。

流れは `app.html` と同じ（メニュー → 宛名番号入力 → 検索 → 結果の行 → 印字項目＋プレビュー → 発行 → 確認「はい」）。違うのは印字画面だけ:

- **検索結果の行をクリックして印字画面に着くと、裏で印刷プレビューの作成が始まる**（`PREVIEW_BUSY_MS = 3000`）
- 作成中は**くるくる**が出る。回っているのは **CSSアニメーション（`@keyframes mock-spin` の `transform: rotate`）だけで、DOMは一切変わらない**
- 作成中に**プレビューアイコンを押しても何も起きない**（ハンドラの先頭で `if (busy) { return; }`。エラーも出ない）
- **プレビューができていないと「発行」が効かない**（確認ダイアログが出ず、代わりに「プレビューを作成してから発行してください」と出る）

最後の1つは設計書に書かれていない**こちらの設計判断**（§8-1に記載）。
本物のシステムで「押下が無効 → 帳票が出ない」となる筋道を練習ページで観測できるようにするために入れた。

### 3.1 くるくるがDOMを変えないことの実測

行クリックの直後に `MutationObserver`（`childList` / `subtree` / `attributes` / `characterData` 全部）を仕掛け、
くるくるが回っている1.5秒間の変化数を数えた:

```
row-clicked
mut=5                                                    ← 画面切り替えぶんの変化
くるくる中のDOM変化(行クリック直後からの増分): 0 / busy表示=true
アイコン押下(作成中) → プレビュー: 未                     ← 押しても効かない
busy終了後のDOM変化(累計増分): 1                          ← くるくるを消した1回だけ
アイコン押下(作成中) → プレビュー: 済                     ← 作成後は効く
```

ページ側の記録（実測）:
```
[{"ev":"busy-start","t":1787897700150},{"ev":"preview-click","t":1787897701686,"busy":true},
 {"ev":"busy-end","t":1787897703277},{"ev":"preview-click","t":1787897704213,"busy":false}]
```
→ 作成にかかった時間 **3,127ms**。**回っている間のDOM変化は0**。
ツールの「画面が落ち着くまで待つ」（DOMが `stable_ms` 変化しないこと）がすり抜ける条件を満たしている。

## 9. 設計書から離れた点・こちらの判断で埋めた点

1. **練習ページで「プレビューができていないと発行が効かない」ようにした。**
   設計書は「押下が無効になる」ところまでしか書いていない。
   G14の合格条件は「失敗または帳票が出ない」なので、その両方が観測できるようにこの作りにした。
   本物の業務システムも「プレビューを作ってから出す」流れなので、無理のない模擬だと考えている。
2. **新しい画面を `app.html` / `spa.html` に足さず、別ページ（`slow.html`）にした。**
   既存の2つに待ち時間を入れると、G2・G6・G9 が今回の追加に引きずられて測れなくなるため。
   設計書は「練習ページに足す」としか書いていないので、足す場所はこちらで決めた。
3. **待ちの一覧の書式。** 設計書の例は `2: click 証明書発行`（セレクタなし）だが、
   同じ節に「記録終了時にすでに出している手順一覧と同じ番号・同じ書式にすること」とある。
   後者を採り、記録中の一覧とまったく同じ説明文（`click #link-shomei-slow (証明書発行（プレビュー作成あり）)`）にした。
   番号の付け方（全手順に1から）は設計書の例と同じ。
4. **空のカンマ（`8,,11` のような入力）は警告を出さずに読み飛ばす。**
   設計書は「数字以外・範囲外」を不正としている。空文字はどちらでもないので、打ち間違いの余地として黙って飛ばす扱いにした。
5. **同じ番号を2回書いた場合は1回だけ採用する**（重複は無視）。設計書に記載がないので決めた。
6. **複数指定したときは番号の小さい順に印を付ける**（表示もその順）。設計書に記載がないので決めた。
7. **待っている間 `  (操作後の待ち: 5000 ms)` と画面に出す。**
   設計書に指定はないが、5秒×件数ぶん黙って止まると固まったように見えるため入れた。

## 10. 未実測・未解決・気になっている点

1. **`final` の手順に `wait_after` を付けた場合は未実測。**
   設計書は「final 以降は実行しないので、そこに付いた印は自然に効かない」としており、
   コードもfinalの手前で打ち切るので実行されないはずだが、**その記録を作っていないので測っていない**。
2. **`goto` / `fill` / `setcheck` / `expect_url` に印を付けた場合は未実測。**
   実装は type を見ずに一律で待つ（`Invoke-CapAction` の直後に待つ）ので同じに動くはずだが、実測したのは `click` に付けた場合だけ。
3. **待ちの秒数は帳票ごとに変えられない。** `wait_after_ms` は設定1個で全帳票・全手順に効く。
   設計書のとおりだが、「10秒待たせたい画面」と「3秒でよい画面」が混ざると、遅い方に合わせることになる。
4. **くるくるの目印を見ない割り切りなので、実機で作成時間が `wait_after_ms` を超えると同じ症状に戻る。**
   §5.3 のとおり、そのときは同じ失敗の仕方（プレビューが効かない→帳票が出ない）になる。
   本番では最初に長めの値から始めて詰めるのがよい。
5. **練習ページのくるくるは3秒の設定だが、実測は 3,127ms / 3,743ms / 3,766ms と伸びる。**
   検証中のEdgeが前面に無いとき、Chromiumがタイマーを間引くため。本番の実測には影響しない。
6. **v3 §8 の未解決点はそのまま**（役割属性の無いただのsvgは記録されない／`<use>` 自身が対象になる経路は未実測／
