## 2. 修正内容のレビュー

### 2.1 見立ては当たっている（ただし穴は統括の見立てより広い）

- `click()` は HTMLElement のメソッドで、SVG要素にはない。実測（Edg/151）:
  ```
  svgに click() があるか: tag=svg typeof click=undefined rect=22
  ```
- **記録側が svg 自身を対象にする経路は、統括が指した900行目付近の行だけではない。**
  `clickTarget()` の**1行目**
  ```js
  var t=t0.closest("a,button,[role=button],[role=tab],[role=menuitem],[role=link],[role=option],li,[onclick],[tabindex]");
  ```
  は `closest` が自分自身も見るため、`<svg role="button">` や `<svg tabindex="0">` は**ここで svg 自身が返る**。実測:
  ```
  記録側 clickTarget が返す相手: svg id=icon-preview     ← use要素からの closest の結果
  虫眼鏡側 clickTarget が返す相手: BUTTON id=btn-search-icon
  ```
  さらに、その下の「祖先を5階層さかのぼる」ループも `cursor:pointer` の svg を返しうる。
  つまり**アイコン用に足した最後の行を直すだけでは塞がらない**。
- 修正は**再生側の `go()`** に入っている。どの経路で svg が記録されても効くので、置き場所として妥当。
  記録側で「svgなら親のHTML要素へ上げる」直し方もあり得るが、押す場所によって動きを変えるページでは結果が変わる。
  コード中のコメント（「押す相手は記録した要素そのもの」）の判断を支持する。
- `rawClick()` は pointerdown → mousedown → pointerup → mouseup → click を `bubbles:true` で要素そのものに投げる。
  **祖先へ伝播で届くことを単体で実測した**（絵の部分 `<use>` に投げて、親 svg のハンドラが動いた）:
  ```
  svg: typeof click=undefined | 前: プレビュー: 未 | use にrawClick後: プレビュー: 済
  ```
- `typeof e.click==='function'` の分岐なので、HTMLの要素（ボタン・リンク・input）の挙動は一切変わらない。G2・G9で実測（後述）。

**結論: 修正はこのまま進めてよい。** 差し戻す理由は見つからなかった。

### 2.2 気づいた点（今回は直していない・報告のみ）

1. **`click` の MouseEvent に `detail: 1` が入っていない。** `event.detail`（クリック回数）を見て処理を分けるUIだと素通りする可能性がある。付けても害はない。
2. **PointerEvent に `pointerId` / `pointerType` / `isPrimary` を渡していない。** `pointerType` は空文字になる。
   `pointerType === 'mouse'` を条件にするライブラリだと効かないことがある。
3. **`e.click()` と違い、rawClick は要素にフォーカスを当てない。** フォーカス移動を前提にした画面では差が出るかもしれない。
4. **これは今回の修正とは別の穴**: 再生側の `visible()` は `e.offsetParent !== null` を先に見るが、
   SVG要素に `offsetParent` は無く `undefined` になるため、この判定は**常に true** になる。
   ＝非表示のアイコンでも「見えている」と判定される。今回の検証では実害は出ていない。
   直すなら `getClientRects().length > 0` を先に見る形になる。**設計書に記載のない挙動なので、勝手には直していない。**
5. `setcheck` 側の `el.click()`（403行目）はチェックボックス/ラジオ（＝HTMLのinput）にしか当たらないので影響なし。

## 3. 練習ページに足したもの（`test/mock/`）

本物の業務システムでよくある「絵だけのボタン」を2種類、帳票出力の流れの中に置いた。**通常遷移版（`app.html`）とSPA版（`spa.html`）の両方**に入れてある。

### 3.1 共通: アイコンの元絵（sprite + use）

`<svg><symbol>` を画面上部に隠して置き、各アイコンは `<use href="#…">` で参照する。
本物の業務システムでよくある作りで、**人がつつく場所（イベントの発生元）が `<use>` 要素になる**。

### 3.2 検索欄の虫眼鏡アイコン（`<button>` の中に `<svg>`）

```html
<button id="btn-search-icon" class="icon-btn" title="検索"><svg …><use href="#spr-search"></use></svg></button>
```

- 「検索」ボタンと同じ検索処理を呼ぶ（どちらから押しても同じ動き）
- 絵の上をクリックしても `clickTarget` は **button** を返すので、再生では従来どおり `e.click()` が使われる。**落ちない側の見本**

### 3.3 印字画面のプレビューアイコン（ボタンに包まれていない `<svg>` 自身がボタン）

```html
<svg id="icon-preview" class="icon" role="button" tabindex="0" aria-label="プレビュー" …><use href="#spr-eye"></use></svg>
```

- `role="button"` と `tabindex="0"` を付け、**svg要素そのものに click ハンドラを付けている**
- 押すと「プレビュー: 済」に変わり、プレビュー欄が開く
- **`clickTarget` が svg 自身を返す条件を確実に踏む**（実測済み・§2.1）
- 発行時に「プレビューを押したかどうか」も発行済みリストに積むようにした。
  → **エラーが出なかっただけでなく、アイコンのハンドラが本当に動いたか**が結果から分かる

### 3.4 その他

- `mock.js` の発行済みリスト表示に「プレビュー:済/未」を追加
- `mock.css` にアイコン用の見た目を追加
- 記録の流れ（両版とも）: メニュー → 宛名番号入力 → **虫眼鏡アイコン** → 検索結果の行 → 印字項目4つ → **プレビューアイコン** → 発行 → 確認「はい」

## A. 変更内容のレビュー — このまま進めてよい

改訂後の `rawClick`:

```js
var m={bubbles:true, cancelable:true, composed:true, view:window,
       clientX:x, clientY:y, screenX:x, screenY:y,
       button:0, buttons:1, detail:1};
var p={}; for(var k in m) p[k]=m[k];
p.pointerId=1; p.pointerType='mouse'; p.isPrimary=true; p.width=1; p.height=1; p.pressure=0.5;
try { e.dispatchEvent(new PointerEvent('pointerdown', p)); } catch(_){}

try { if(typeof e.focus==='function') e.focus({preventScroll:true}); } catch(_){}
… pointerup / mouseup / click は buttons:0・pressure:0
```

妥当と判断した点:

- **`buttons` の値の付け方が正しい。** 押している間（pointerdown / mousedown）は `1`、離した後（pointerup / mouseup / click）は `0`。
  実際のブラウザのイベントと同じ。`pressure` も 0.5 → 0 で、押している間だけ圧がある形になっている
- **`focus()` の位置が mousedown の直後**。本物のブラウザもフォーカスは mousedown の時点で移るので、順番が合っている
- `typeof e.focus==='function'` と `try/catch` の二重の保護があり、フォーカスできない相手でも落ちない
- `preventScroll:true` があるので、フォーカスで画面が勝手にスクロールしない
- JSはPowerShellの展開可能ヒアストリング内にあるが、**`$` もバッククォートも含まれていない**ことを確認した（＝ブラウザに届くJSが壊れない）

細かい点（実害なし・直す必要は無いと考える）:

1. PointerEvent 側にも `detail:1` が入っている。本物の pointerdown は `detail` が 0。`event.detail` で押し方を見分けるページは事実上ないので実害なし
2. `screenX/screenY` に画面座標ではなく画面内座標を入れている。ウィンドウの位置ぶんずれるが、これを使う画面はまずない

## D. `e.focus()` の副作用の確認 — 副作用は出ていない

練習ページは書き換えず、**CDPからページに見張りを注入して、再生中に起きた `focusin` / `focusout` / `change` / `input` を全部書き留めた。**

### D-1. 通常遷移版・SPA版を1件ずつ流したときのイベント（全件）

```

  02. change target=input#input-atena  active=input#input-atena
  03. input  target=input#chk-setai    active=body
  04. change target=input#chk-setai    active=body
  05. input  target=input#chk-zokugara active=body
  06. change target=input#chk-zokugara active=body
  07. input  target=input#chk-honseki  active=body
  08. change target=input#chk-honseki  active=body

  10. change target=input#chk-mynumber active=body
```

（通常遷移版・SPA版とも同じ10行。どちらも最後は正しく発行され、画面は元に戻り、入力欄は空になっている）

- **ツールが自分で投げている `input`/`change` 以外は1つも増えていない。**
- 余計な `change`（＝入力欄から抜けたことによる確定処理）は**起きていない**

### D-2. なぜ focusin/focusout が上の記録に出てこないか（確認済み）

**ウィンドウが前面に無いあいだ、Chromium はフォーカス系のイベントを発火しない**（`document.activeElement` は変わる）。
`document.hasFocus()` が `False` のときは記録に出ず、`Page.bringToFront` で前面に出して `True` にすると出る。実測で確かめた。
つまり D-1 に出ていないのは「focus していない」からではない（G6の `activeElement=svg#icon-preview` が動いている証拠）。

### D-3. 前面に出した状態での、フォーカス移動そのものの中身

```
##### 1. ツールと同じやり方（値を直接代入）で入力欄を埋め、別要素にフォーカスを移す
    - focusout target=input#input-atena active=body
    - focusin  target=button#btn-search active=button#btn-search      ← change は出ない

##### 2. 人が実際に打ち込んだ場合（比較用）に、別要素にフォーカスを移す
    - change   target=input#input-atena active=body                    ← こちらは出る
    - focusout target=input#input-atena active=body
    - focusin  target=button#btn-search active=button#btn-search

##### 3. 印字画面で、改訂後の rawClick をアイコンに投げる
    - focusin target=svg#icon-preview active=svg#icon-preview
  結果: プレビュー: 済 / activeElement=svg#icon-preview
  画面: 検索=false 結果=false 印字=true 確認=false                     ← 画面は変わっていない
```

**要点:** ブラウザは「人が打ち込んだ欄」から抜けるときだけ `change` を出す。
ツールの `fill` は値を直接代入するので打ち込み扱いにならず、**フォーカスが外れても確定処理は走らない。**
（2は比較のために `Input.insertText` で本当に打ち込んだ場合。人が手で操作したときと同じ挙動で、ツールの動きではない）

- 画面が切り替わる・確定処理が走るといった副作用は、練習ページでは**起きていない**
- 逆に、**「入力欄から抜けたときに確定する」作りの本物のシステムでは、この `focus()` は人の操作に近づく方向に働く**
  （従来は `click()` でもフォーカスは移らなかった）

## E. 追記時点で残っている懸念

- `focus()` は**押した相手にフォーカスを乗せたまま**次の手順に進む。本物のシステムに
  「フォーカスが当たっている間だけ出るツールチップ・サジェスト」があると、次のクリックの当たり判定に影響する可能性がある（練習ページでは再現できない）
- 本番で「フォーカスが移ったせいで画面が変わった」が疑われるときは、`rawClick` の `focus()` の1行だけを外して比べれば切り分けられる
- §8 の未解決点（役割属性の無いただのsvgは記録されない／`<use>` 自身が対象になる経路は未実測／`visible()` がSVGで常に真）は**そのまま**。今回の改訂では触れられていない
