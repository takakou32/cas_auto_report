### 記録（-Record）をどう自動で回したか

`-Record` は `[Console]::KeyAvailable` でEnter待ちをするため、標準入力がパイプの状態（WSLからの実行）では止められない。
そこで**本物のコンソールを持つ別プロセスとして記録を起動し、ブラウザ操作はCDPの2つ目のクライアントから流し込み、終了のEnterは
`AttachConsole` + `WriteConsoleInput` で対象プロセスのコンソール入力バッファへ直接書き込んだ**（前面化・SendKeysは使っていない。
使用者のデスクトップに勝手なキー入力を飛ばさないため）。ブラウザ側の操作はすべて実際のDOMイベント（`element.click()` 等）で行っている。
本体スクリプトには一切手を入れていない。

## 3. SPA版（pushState）で見つかった重大な問題

設計書 §6 は「通常遷移版とSPA版の両方が理想。最低限どちらか一方＋もう一方は口頭説明」としているが、
説明で済ませずに **SPA版の練習ページ（`test/mock/spa.html`）も作って実測した**。結果、看過できない問題が出た。

### 何が起きたか

SPA版（画面遷移のたびに `pushState` でURLが変わる）を記録すると、**クリックが1つも残らない**:

```
  手順 1: goto http://localhost:8765/spa.html#/menu
  手順 2: goto http://localhost:8765/spa.html#/search     ← メニューのリンククリックが消えた
  手順 3: fill #input-atena = 1234567890
  手順 4: goto http://localhost:8765/spa.html#/result     ← 「検索」ボタンのクリックが消えた
  手順 5: goto http://localhost:8765/spa.html#/print      ← 検索結果の行クリックが消えた（＝宛名番号の写り込みも消えた）
  手順 6〜9: setcheck ×4
  手順 10: goto http://localhost:8765/spa.html#/menu      ← 「発行」ボタンのクリックまで消えた

記録した手順数: 10
SPA(クライアントサイド遷移)を検出 → spa_mode=true で保存します
宛名番号を {{atena}} に置換: 1 箇所          ← 通常版は2箇所。行クリックのtextが消えたため
クリックが記録されていないため、出力実行ボタン(final)を設定できません。
```

原因は、設計書 §4.7・§5 が「そのまま流用」と指定した cas_cap の記録ロジック:
**クリックの直後にURLが変わったら、そのクリックは「遷移を起こしただけ」とみなして捨て、宛先URLへの `goto` に置き換える。**
撮影ツール（cas_cap）なら結果は同じ画面になるので問題ないが、本ツールでは
「検索の実行」「対象者の選択」「出力の実行」という**押すこと自体に意味があるクリック**まで消えてしまう。

### 再生した結果（実測）

```powershell
.\powershell\cdp_print.ps1 -Job R002_住民票SPA     # 対象3件
```

```
[R002_住民票SPA] 1234567890 : 処理中... 完了
[R002_住民票SPA] 1234567891 : 処理中... 完了
[R002_住民票SPA] 1234567892 : 処理中... 完了
処理件数: 3 件
```

```csv
job,atena,timestamp,status,error
R002_住民票SPA,1234567890,2026-08-27 19:32:32,ok,
R002_住民票SPA,1234567891,2026-08-27 19:32:36,ok,
R002_住民票SPA,1234567892,2026-08-27 19:32:39,ok,
```

**発行済みリスト: 0件。** つまり **台帳に3件 ok と書かれているのに、帳票は1枚も出ていない。**
設計書 §4.4 が防ごうとした「誤った対象で出力する事故」の一歩手前の状態（＝黙って何もしない／状態が残っていれば前の対象者で出す）が、
SPAでは普通に起こりうる。

### 併せて見つかったこと

- `spa_mode=true` だと **すべての `goto` が pushState になる**ため、記録の1手順目がアプリ外のページ（メニューHTML等）だと、
  再生時にそのページを本当には読み込めない。SPAの場合、記録は**必ずアプリの中の基準画面から**始める必要がある
- 通常遷移版（`app.html`：URLを変えずに画面を切り替える作り＝ポストバック型）では、この問題は起きない（G1〜G6のとおり）

### 対処案（実装していない。設計判断が要るため）

1. クリックを goto に置き換えず、**click を残したうえで goto を続ける**（クリックが効いていれば goto は同じURLへの再遷移で無害）
2. `final`（出力実行）だけは絶対に click として残す
3. 少なくとも「クリックが1つも記録されなかった」場合は、現状の警告だけでなく**保存を止める**

**設計書と矛盾するため、勝手には直していない。** 判断を仰ぎたい。

## 4. 設計書から逸脱した点・解釈で埋めた点

1. **`-Evidence` パラメータを追加した（逸脱）**
   設計書 §4.3・§4.8 では証跡は設定ファイルの `evidence` で決めるが、§4.9 のGUIには「証跡のチェック」がある。
   GUIから渡す口が無いと成立しないため、`-CdpUrl` が `cdp_url` を上書きするのと同じ流儀で
   `-Evidence none|before|after|both` を追加し、GUIのチェックONで `-Evidence both` を渡している。指定しなければ設定ファイルの値を使う。
2. **DryRun時の証跡は `before` のみ撮る（解釈）**
   `after` は出力ボタンを押した後の画面のことなので、押さないDryRunでは撮っていない。
3. **`setcheck` の再生時に `label` をフォールバックに使う（解釈）**
   設計書のJSON例に `label` はあるが用途の記載がない。`click` がセレクタとボタン名のハイブリッド特定をしているのに合わせ、
   セレクタで当たらないときだけ項目名でチェックボックスを探す保険にした。
4. **手順ファイルの `target_url_keyword` を対象タブ探しに優先して使う（解釈）**
   設計書 §4.7 で手順ファイルに `target_url_keyword` を持たせているため、帳票ごとに接続し直し、
   手順ファイルの値があればそれを、無ければ設定ファイルの値を使う。
5. **`jobs/` `targets/` `output/` に `.gitkeep` を置いていない（解釈）**
   設計書指定の .gitignore（`output/*` 等）と衝突するため。必要なディレクトリはスクリプトが実行時に作る。
   `targets/` だけは使用者が自分で作る（README に記載）。
6. **`goto` の URL は `{{atena}}` 置換の対象にしていない（設計どおり・要注意）**
   設計書 §4.2 は置換対象を fill の値・click の text/selector に限定している。そのため
   **検索が GET で URL に宛名番号が乗る作りの画面（`?atena=1234567890` 等）では、記録した1人目のURLに固定されてしまう。**
   練習ページはURLに宛名番号が乗らない作りにしてある。実システムがGET型なら設計の見直しが要る。
7. **`fill` の置換は完全一致のみ（設計どおり）**
   設計書 §4.2-1 が「value が -Atena の値と一致」なので、前ゼロ・ハイフン付きなど**入力欄の値が加工される画面では置換されない**。
   その場合は記録時に「置換 0 箇所」の警告が出る。

## 5. 未解決・気になっている点

1. **SPA（pushState）で使えない。** 上記 §3。本ツールの想定環境（設計書 §2「SPAの可能性あり」）に直撃するので、二周目の最優先事項。
2. **DryRun でも台帳に `ok` が入る。** 設計書 §4.3 は DryRun を台帳の例外にしていないのでそのまま実装したが、
   試し実行のあとに本番を流すと**その人が「処理済み」で飛ばされる**。README に注意書きを入れたが、仕様として直したほうがよいかもしれない。
3. **`final` は「最後のクリック」でしか付かない。** 出力ボタンのあとに確認ダイアログのOKが要る画面（実システムにはよくある）だと、
   `final` が付くのは最後のOKになる。DryRunはOKの手前で止まるが、その時点で出力ボタンは押されている＝帳票は出てしまう。
4. **練習ページと本物の差。** 練習ページは要素にIDがある素直な作り。実システムのIDが自動生成（`pv_id_` 等）だと
   セレクタは `nth-of-type` を含む位置指定になり、権限差・件数差で当たらなくなる可能性がある（cas_cap の cssPath をそのまま使っているので、
   その弱さもそのまま引き継いでいる）。
5. **`select`・`wait`・`keyboard` アクションは未実測。** 練習ページに該当操作が無いため。cas_cap から無改造で流用した部分。
6. **GUIランチャー（`gui/launcher.ps1`）は構文チェック（G7）のみ。** 画面を出しての操作は未実測（WinFormsの表示を伴うため）。
7. **`ready_selector` を指定した場合の待機は未実測。** 練習ページが即描画なので効果を測れていない。
